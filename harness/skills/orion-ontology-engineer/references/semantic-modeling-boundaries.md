# 语义建模边界与当前工程内复用

在 S2 首次设计、S3 规则绑定或 S4 报 `G-S4-REASONING-TERMS` 时读取。以下是建模判断方法，不是可复制的生产事实或通用载荷模板；字段始终以当前工具 schema 为准。

## 先区分对象、经历、派生定义与查询结果

| 语义角色 | 选择依据 | 示例与禁止事项 |
| --- | --- | --- |
| 领域实体 | 有跨问题稳定身份、属性和生命周期 | 候选人、项目、组织、技能。不能把每个 CQ 的命中集升级为核心实体。 |
| 参与经历或关系事件 | 同一关系有角色、本人技术使用、起止时间、证据等多项属性 | 候选人参与项目的一段经历；候选人、项目、经历分别有稳定 ID。项目总时长不等于本人参与时长。 |
| 可复用派生类或关系 | 有独立、稳定且已批准的业务定义，并有可执行推导依据 | “医疗信息化项目”可在定义充分时成为派生类；二元“候选人在某经历上满足条件”必须保持关系或经历语义。 |
| 参数化查询结果 | 随时间窗口、阈值、角色集合或一次筛选条件变化 | “最近两年 Python 累计满一年的人”优先保留查询参数、计算依据及结果合同；不创建永久的“2026年9月合格候选人”核心类。 |

先在当前 S2 草稿中明确每个候选的角色和来源，再写 S3 Mapping。`kind` 和 `mapping_type` 使用公开 schema 支持的值；上述“语义角色”不是新增必填 JSON 字段。不为通过门禁添加无来源类，也不擅自删除已批准的分类。

## 同一经历上的条件必须共同成立

筛选“医疗项目、本人用 Python、技术负责人、本人参与至少半年”时，应沿同一个参与经历标识绑定全部条件。不能把候选人在 A 项目使用 Python、在 B 项目任负责人、C 项目持续半年拼成一个命中；只按候选人 ID join 不充分。若来源只有项目描述、没有本人职责/起止时间，分别保留缺口，不把团队技术栈当本人使用事实。

可用概念路径是 `Candidate → Participation → Project`，角色、本人技术使用与起止日期落在对应参与经历上；这是设计选择示意，不能直接复制成当前工程的事实。现有设计若把 ResumeProject 定义为“本人项目经历”而非共享项目实体，应先核对稳定身份和语义是否一致，再决定保留或修订。

## 数据类型与计算证据一起定义

- 数值、年月、日期、布尔与标识符分别确定 datatype；月份数不应成为任意字符串。仅有年月的材料不要伪造具体日期，说明年月表示与区间边界。
- 累计经验先定义窗口起止、是否含首尾月、重叠经历去重、开放结束日期和缺失日期策略。累计月份并集不等于项目月数直接相加；“满一年”与“超过一年”不能混用。
- datatype 必须贯穿 S2 属性语义、S3 Mapping/fact binding、S4 属性 range、S5 RDF literal 和 S6 查询比较。规则引擎当前不支持比较/区间并集时，记录算子缺口或使用已受管且有回执的计算能力；不得先手算正例再把 `AtLeast12` 当成原始事实。
- 远程意愿“明确接受”“明确拒绝”“未写明”分别记录。完整材料中未提及只能支持“该材料未写明”，不能支持现实中拒绝或接受；资料不完整还应保留“未核验”。闭世界结论须绑定完整来源范围和版本。

## 规则术语声明不是扩充核心类的命令

`G-S4-REASONING-TERMS` 表示事实/结论谓词的 `ontology_terms` IRI 没有完整进入本体声明，不表示每个谓词都必须是 class。先检查谓词元数和含义：一元成员判断、对象间二元关系、对象到 literal 的数据属性应保持各自语义；更高元事实需要明确经历/事件承载及执行器支持。不要把二元 `PersonalPythonUse(candidate, participation)` 声明成一个类来凑 IRI，也不要把数值统计变成无依据的分类。

对于业务认可的派生类别或 CQ 结果关系，可以声明所需术语并注明派生依据、作用范围及参数绑定；它们不能与领域核心对象混为一谈。若平台编译器只提供不相容的声明方式，保留失败与受影响 CQ，归责平台能力缺口，不通过机械加类、放宽门禁或降级 `NOT_APPLICABLE` 修复。

## 用当前工程的证据与合同完成一次载荷

1. 回读绑定工程 `get_ontology_workflow_status`、`get_next_workflow_action` 与正式 S0/S1 证据；当前 S2 `capability-plan.json` 用于能力路由，不能替代业务定义或真实实例。
2. S2 草稿包含完整原始 CQ 的 `cq_semantic_assessments`；规则条件、来源、反例和边界与候选共同检查。当前目录提供时，先 `get_stage_input_contract(project_id, stage)` 取得当前来源模式的合同、空骨架和正式来源引用，再 `save_stage_submission(project_id, stage, payload, expected_revision)` 由平台保存完整受控草稿并预检。后续优先对返回的真实 `payload_file` 使用 `patch_stage_submission` 局部修正；平台仍校验合并后的完整载荷及原始 CQ、规则与来源一致性，不删减未修改内容。不要为写草稿遍历目录或调用 bash。旧工具目录没有相应入口时，才使用现有 `preflight_stage_submission` 的 `payload_file` 和真实 SHA-256。成功后 token commit 且 `response_mode="SUMMARY"`；空骨架本身不是合法语义方案。
3. S3 先按 `intake_mode` 选择 schema 分支。`DOCUMENT_ONLY` 不复制 Ontop 配置；文档事实与规则分别填写当前 schema 要求的 `document_fact_queries` 和能力内 `rules`，不能以已有规则文件名替代所需字段。`fact_bindings` 对齐当前事实行的字段位置/类型以及同一实体或经历的标识。事实数量由全部选定资料决定，不固定为示例人数。
4. 若预检返回 `repair_contract`，在当前草稿一次修正所列问题，保留业务范围和全部 CQ；不遍历别的工程寻找可复制通过的事实、标识符、规则和结果。当前正式产物和同工程已有决定才是复用起点。
5. S4 优先 `generate_ontology_design` 的确定性生成路径。先检查生成设计是否保留以上语义，再提交整套设计审阅；技术 IRI 补齐不能代替语义审阅。需修改已通过 S2/S3 时走正式 rollback preview/reopen，不直接覆盖正式产物。

质量核对至少包含跨经历混配反例、重叠月份边界、日期缺失、远程未提及和明确拒绝的区分；这些是验收条件，不是让模型创造生产记录。保留真实材料无法支持的未知结果。
